## 1. What is a Project?

A **Project** in PLCAutoPilot is the primary container for a real-world PLC automation job.
It groups every artefact — documents, generated code, HMI scripts, AI chat history,
uploaded wiring diagrams, error fixes, and PLC recommendations — that belong to a single
automation job from first requirements through commissioning.

### The mental model

```
Project  (e.g. "Bottling Line Phase 2")
├── Metadata      name, description, PLC target, industry, status, tags
├── Programs      generated PLC code files (all revisions)
├── HMI Scripts   vendor HMI scripts + tag CSVs generated by the HMI generator
├── Uploads       wiring diagrams, P&IDs, datasheets, photos, any file the user attaches
├── Chats         AI Co-Pilot and Engineer Chat sessions scoped to this project
├── Rectifications error fixes applied against programs in this project
├── Recommendations PLC selection recommendations made in context of this project
└── Activity log  every mutation with timestamp and user (audit trail)
```

A project does **not** duplicate the generation tools — it is a lens that scopes them.
When you generate a program with a project selected, the result is stored inside that project.
When you open a project you see everything in one place.

## 3. Architecture principles (keep from v1.6)

1. **DB access only in `lib/db/queries.ts`** behind `requireUser()`. Routes stay thin.
2. **Prompts and AI in Python.** BFF routes are thin proxies. Scoping to a project is done in the BFF layer (pass `projectId` in the job payload; Python stores it via the callback).
3. **`fileOperations` table is the canonical file store.** Actual bytes go to an object storage URL (`storageUrl`). For v1.7 local dev, store files in `public/uploads/projects/<projectId>/` and set `storageUrl` to the relative path. Cloud storage (S3/Supabase Storage) is a config swap, not a code change.
4. **No new page framework.** All pages are Next.js `app/` RSC or `'use client'` consistent with the rest of the app.
5. **Backward compat.** Programs generated without a project still work; `projectId: null` is valid everywhere.

## 4. Data model changes

### 4.1 `projects` — add columns

Current columns: `id, userId, organizationId, name, description, plcManufacturer, plcModel, programmingLanguage, applicationType, status, createdAt, updatedAt, metadata`.

Add:

| New column | Type | Purpose |
|-----------|------|---------|
| `templateId` | `varchar(100)` nullable | Which `ProjectTemplate.id` this was created from |
| `industry` | `varchar(100)` nullable | Industry tag (mirrors `ProjectTemplate.industry`) |
| `tags` | `jsonb` default `[]` | Free-form tags array for filtering |
| `coverImage` | `text` nullable | `storageUrl` of a cover photo / P&ID thumbnail |

No breaking changes to existing rows; all new columns are nullable / have defaults.

### 4.2 `project_chats` — new table

Chat sessions (`chatSessions`) currently have no project FK. Rather than alter that table (breaking change), add a join table:

```sql
CREATE TABLE project_chats (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  project_id  UUID NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  session_id  UUID NOT NULL REFERENCES chat_sessions(id) ON DELETE CASCADE,
  created_at  TIMESTAMP DEFAULT now()
);
CREATE INDEX idx_project_chats_project ON project_chats(project_id);
CREATE INDEX idx_project_chats_session ON project_chats(session_id);
```

### 4.3 `project_notes` — new table

Lightweight markdown notes the user writes inside the project (requirements, commissioning notes, etc.):

```sql
CREATE TABLE project_notes (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  project_id  UUID NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  user_id     UUID REFERENCES users(id) ON DELETE SET NULL,
  title       VARCHAR(255) NOT NULL DEFAULT 'Note',
  body        TEXT NOT NULL DEFAULT '',
  created_at  TIMESTAMP DEFAULT now(),
  updated_at  TIMESTAMP DEFAULT now()
);
CREATE INDEX idx_project_notes_project ON project_notes(project_id);
```

### 4.4 Existing tables that already have `project_id` (wire, don't change)

| `learning_data` | `project_id` | Pass from BFF |

## 7. Phase C — File uploads

**Goal:** users can attach any file (wiring diagram, P&ID, datasheet, photo) to a project. For v1.7 local dev, files are written to `public/uploads/projects/<projectId>/`. Cloud storage is a later config swap.

### C1 — Upload API

`POST /api/projects/[id]/files` — `multipart/form-data`:
- Accept up to 50 MB per file; reject outside MIME allowlist (images, PDF, CSV, `.xml`, `.json`, `.zip`).
- Write file to `public/uploads/projects/<projectId>/<uuid>-<originalName>`.
- Insert row into `file_operations`: `projectId`, `operationType: 'user_upload'`, `fileName`, `fileSize`, `mimeType`, `storageUrl` (relative `/uploads/...`).
- Return `{ file }`.

`DELETE /api/projects/[id]/files/[fileId]` — delete the DB row + disk file.

### C2 — Files tab UI

Drop zone component in the Files tab:
- Drag-and-drop or click to browse.
- Shows thumbnail for images, PDF icon for PDFs, generic icon otherwise.
- Shows filename, size, upload date.
- Delete button with confirmation.
- Download link for re-accessing the file.

### C3 — Storage abstraction

`lib/storage.ts` — thin module:
```ts
export async function writeFile(projectId: string, filename: string, buffer: Buffer): Promise<string>
export async function deleteFile(storageUrl: string): Promise<void>
```

For v1.7: writes to `public/uploads/`. For a future cloud swap, change this module only.

### Acceptance (Phase C)

- Upload a PNG → appears in Files tab with thumbnail.
- Upload a PDF → appears with icon + download link.
- Delete file → removed from UI and disk.
- Files over 50 MB are rejected with a clear error.
- Accepted MIME types enforced server-side (not just client).

## 8. Phase D — Chat linkage

**Goal:** when starting an AI Co-Pilot or Engineer Chat session, users can optionally associate it with a project. Linked sessions appear in the project's Chats tab.

### D1 — Link session to project

`POST /api/ai-chat` and `POST /api/ai-engineer-chat` — accept optional `projectId`.
On the first message of a session, if `projectId` is provided:
- Create/reuse a `chatSessions` row.
- Insert into `project_chats (project_id, session_id)`.

### D2 — Chats tab UI

Lists linked chat sessions: engineer name or "AI Co-Pilot", start date, message count, last message preview.
Click → expands to show the full message thread (read-only replay).

### D3 — Project context in AI prompt (optional enhancement)

If a session is linked to a project, prepend a short context block to the system prompt:
```
Project: "Bottling Line Phase 2"
PLC: Siemens S7-1200
Industry: Food & Beverage
```
This gives Claude awareness of the project without any schema change to Python services.

### Acceptance (Phase D)

- Start a chat with project selected → session appears on that project's Chats tab.
- Chat without project → no change from v1.6 behaviour.
- Message thread replay works without calling the AI again.

## 9. Phase E — Templates v2, `/projects` landing, seed, tests

### E1 — Create project from template

Currently "Use template" on `/projects/templates` pre-fills the generator URL.
In v1.7 it also **creates a project** from the template metadata and then redirects to the project workspace.

`POST /api/projects/from-template` — body: `{ templateId, name? }`:
1. Look up `PROJECT_TEMPLATES` by `templateId`.
2. `createProject(user, { name: name ?? template.name, plcManufacturer: template.defaultPlatform, plcModel: template.defaultController, applicationType: template.industry, templateId, description: template.description })`.
3. Return `{ project }` with the new project's `id`.
4. Client redirects to `/projects/<id>?tab=overview&newFromTemplate=1`.

The project is created empty; the generator prefill URL is surfaced as a quick-action button on the Overview tab ("Generate program from this template").

## 10. Extended data model (stretch / v1.8-ready)

These are designed now but not implemented in v1.7. Document them so the v1.7 schema migration leaves room.

### 10.1 `project_activity` — audit log

```sql
CREATE TABLE project_activity (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  project_id  UUID NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  user_id     UUID REFERENCES users(id) ON DELETE SET NULL,
  event_type  VARCHAR(100) NOT NULL,   -- 'program_generated', 'file_uploaded', 'status_changed', ...
  event_data  JSONB DEFAULT '{}',
  created_at  TIMESTAMP DEFAULT now()
);
CREATE INDEX idx_project_activity_project ON project_activity(project_id);
```

Populated by the same `logUsage` pattern used for `usage_analytics`, but project-scoped.

### 10.2 `project_templates` — user-defined templates

```sql
CREATE TABLE project_templates (
  id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id       UUID REFERENCES users(id) ON DELETE CASCADE,
  org_id        UUID REFERENCES organizations(id) ON DELETE CASCADE,
  name          VARCHAR(255) NOT NULL,
  description   TEXT,
  industry      VARCHAR(100),
  plc_manufacturer VARCHAR(100),
  plc_model     VARCHAR(100),
  pattern       VARCHAR(100),       -- PlcPattern or null for custom
  logic_description TEXT,
  metadata      JSONB DEFAULT '{}',
  is_public     BOOLEAN DEFAULT false,
  created_at    TIMESTAMP DEFAULT now()
);
```

Allows org-level shared templates. Built-in templates from `lib/templates.ts` are code-defined and don't need rows.
